“AI là một người thợ xây cực nhanh, nhưng nó không phải là kiến trúc sư. Hãy giữ quyền quyết định nghiệp vụ, đừng giao phó ‘cái đầu’ của bạn cho máy móc.”

🪤 1. “Vibe Coding”: Cái Bẫy Của Cảm Giác Sung Sướng

Vibe Coding là một cú lừa vay nặng lãi:

┌────────────────────┐
│      TUẦN 1        │ ──► Code lên production nhanh thần tốc.
│ (Vibe Coding)      │ ──► Team sung sướng.
└─────────┬──────────┘
          ▼
┌────────────────────┐
│      THÁNG 3       │ ──► Bug xuất hiện.
│ (Nợ kỹ thuật)      │ ──► Không ai nhớ vì sao code viết thế này?
└─────────┬──────────┘     Ngoại lệ (exception) xử lý ở đâu?
          ▼
┌────────────────────┐
│     HẬU QUẢ        │ ──► Sửa bug cực chậm.
│ (Mất kiểm soát)    │ ──► Không ai dám đụng vào code cũ (Refactor).
└────────────────────┘

Nguyên nhân: Tốc độ tạo code của AI đã bỏ xa khả năng ghi nhận ngữ cảnh (Context) của con người.

🧠 2. SDD: Bắt AI Làm Thợ, Giữ Lấy “Cái Đầu”

Để trị căn bệnh này, các team lão luyện dùng SDD (Spec Driven Development - Phát triển hướng Đặc tả).

Quy tắc rất đơn giản: Chèn một bản Đặc tả (Spec) làm “hợp đồng” giữa cái đầu của bạn và đôi tay của AI.

┌────────────────────────────────────────────────────────┐
│  [ NÃO BỘ ] ──► (Con người chốt Ý tưởng, Logic, Luật)  │
└──────────────────────────┬─────────────────────────────┘
                           ▼
┌────────────────────────────────────────────────────────┐
│  [ SPEC ] ──► (Văn bản chốt hạ Rule, Ngữ cảnh rõ ràng) │
└──────────────────────────┬─────────────────────────────┘
                           ▼
┌────────────────────────────────────────────────────────┐
│  [ THỢ XÂY ] ──► (AI Agent code/test dựa ĐÚNG vào Spec)│
└────────────────────────────────────────────────────────┘

Nguyên lý sinh tử: Nếu có bug, phải tìm và sửa trên file Spec trước, sau đó mới kêu AI sửa code.

📝 3. 4 Câu Hỏi Gom Gọn Trong File Spec

Để AI không đoán bừa, bạn làm chủ “cái đầu” bằng cách trả lời đúng 4 câu hỏi này vào Spec trước khi gõ dòng code nào:

┌─────────────────────────────────────────────────────────┐
│ 1. TẠI SAO LÀM? (Business Requirement - BR)             │
│    Vd: Tăng tỷ lệ thanh toán thành công.                │
├─────────────────────────────────────────────────────────┤
│ 2. AI LÀM GÌ? (Use Case - UC)                           │
│    Vd: User quét mã QR để trả tiền.                     │
├─────────────────────────────────────────────────────────┤
│ 3. KHÁI NIỆM NÀO? (Entity)                              │
│    Vd: Hóa đơn (Order), Cổng thanh toán (Gateway).      │
├─────────────────────────────────────────────────────────┤
│ 4. THẾ NÀO LÀ ĐÚNG? (Acceptance Criteria - AC)          │
│    Vd: Mã QR hết hạn sau 15p thì tự động hủy đơn.       │
└─────────────────────────────────────────────────────────┘

⚖️ 4. Chậm Lại 1 Tuần, Cứu Lấy Cả Năm

                    BÀN CÂN THỰC CHIẾN
┌─────────────────────────┬─────────────────────────────┐
│       VIBE CODING       │    SPEC-DRIVEN (SDD)        │
├─────────────────────────┼─────────────────────────────┤
│ 1. Nhanh ở tuần đầu     │ 1. Tuần đầu chậm hơn (viết Spec)│
│ 2. Mù mờ vào tháng thứ 3│ 2. Ổn định dài hạn (nhờ Spec)│
│ 3. Sửa bug bằng niềm tin│ 3. Sửa bug đọc AC, đọc Test │
│ 4. Prompt quyết định Code│ 4. Spec quyết định Code    │
└─────────────────────────┴─────────────────────────────┘

🎯 5. Tóm tắt bỏ túi (Take away)

Nếu bạn quên hết những gì vừa đọc, chỉ cần nhớ cái bảng này là đủ:

Tiêu chí Điểm mấu chốt
Bản chất Vibe Coding Giao cả não lẫn tay cho AI: Viết code siêu tốc nhưng tạo ra “nợ kỹ thuật” khổng lồ vì mất ngữ cảnh.
Giải pháp (SDD) Bắt AI làm “thợ gõ code”, con người giữ lại “bộ não” nghiệp vụ (Business Rule).
Quy trình chuẩn Mình viết Spec trước ──► AI đọc Spec & phản biện ──► AI viết code.
Cách sửa lỗi Bug ở đâu ──► Cập nhật lại Spec ở đó ──► Yêu cầu AI viết lại code (Không sửa code trực tiếp).
4 Tầng Đặc Tả Trả lời: Tại sao làm? - Ai làm gì? - Khái niệm? - Tiêu chí đúng là gì?
